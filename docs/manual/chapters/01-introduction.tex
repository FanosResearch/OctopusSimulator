\section{The problem}

Modern embedded platforms are multicore, but their adoption in real-time and safety-critical
domains is throttled by \emph{shared-memory interference}: the latency of a memory request
depends not only on the request itself but on the concurrent activity of every other core
across the interconnect, the coherence fabric, the shared cache and the DRAM controller.
Deriving safe \emph{and} tight timing bounds is therefore an end-to-end problem.

The field's first instinct is additive: analyse each resource in isolation, bound the worst
wait at each, and sum. \Cref{ch:request-end-to-end} shows why that is unsafe in a real
hierarchy: resources interact and reorder. A request that was first onto the request bus can
return last because three younger requests hit open DRAM rows and took the response channel
ahead of it; a core whose working set fits its private cache still goes to DRAM because another
core's streaming evicted its lines from an inclusive shared cache. Measured on a four-core
system with round-robin arbitration at every resource, the worst observed latency of the oldest
request was $35\times$ the per-resource bound. Mechanisms proposed in response --- predictable
arbiters, partitioned caches, predictable memory controllers, real-time coherence protocols
--- are each usually prototyped in a bespoke simulator, which makes cross-comparison, reuse and
whole-hierarchy studies difficult.

\section{What Octopus is}

Octopus is a reusable, whole-hierarchy, cycle-accurate substrate in which memory-system ideas
can be built, observed, validated and verified under one roof. Unlike simulators that fix an
architecture, it treats every layer as a configurable, swappable component and makes the hardest
component to change --- the coherence protocol --- an editable spreadsheet rather than C++
(\cref{ch:coherence-engine}). Five capabilities follow, each tied to a mechanism in this manual:

\section{Built on Octopus}

Octopus has been the modelling and evaluation platform for a body of peer-reviewed work on
real-time memory systems, developed since 2018: the simulator itself (IEEE Computer Architecture
Letters, 2024) and its gem5-integrated full-system extension (ECRTS Industrial Challenge, 2025);
the predictable coherence protocols DISCO (ECRTS 2020, IEEE TC 2022), PISCOT (RTSS 2020, ACM
TECS 2022), Duetto (DATE 2021), DUPECO (ECRTS 2022), PCC (ECRTS 2022) and CoHoRT (DATE 2025);
the coordinated arbitration scheme GRROF (ECRTS 2023); and the earlier predictable protocols
PMSI, PMESI, PENDULUM, PMSI* and PMESI*, re-implemented in Octopus so that they can be compared
head to head under identical conditions. \file{PUBLICATIONS.md} keeps the list current.

\section{What it is not}

Octopus is a \emph{timing} model of the memory system. The trace-driven core issues addresses
with compute gaps between them and carries no data values; a periodic task is a fixed compute
budget plus accesses. There is no instruction set, no branch, no data-dependent control flow
--- for those, run it behind gem5 (\cref{ch:integration-modes}). There is no preemption and no
multi-task scheduling on a core. Deadlines are observed and reported, never enforced. The DRAM
model, when not MCsim, is a single fixed latency. These are the lines the demo
(\cref{ch:tasks-and-demo}) is careful to draw between what is measured and what is drawn, and
they are the lines to keep in mind when reading any number out of it.
